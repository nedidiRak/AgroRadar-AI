# AgroRadar AI — технический аудит (02.11.2026)

Проверен **репозиторий `nedidiRak/AgroRadar-AI`, ветка `main`** (на момент аудита). Это статический аудит исходного кода; работоспособность живых сервисов пользователя этим документом не подтверждается.

## P0 — до публикации в интернете

1. **Отсутствует аутентификация/авторизация пользовательских операций.** Маршруты `POST /api/fields`, `PUT/DELETE /api/fields/{id}`, `PUT/DELETE .../geometry` и журнал наблюдений доступны любому клиенту, который может обратиться к FastAPI. CORS не является механизмом авторизации. **Не открывать текущий backend в публичный интернет** до внедрения входа, управления правами и защиты от злоупотреблений.
2. **Геоданные, описания полей и записи осмотров являются пользовательскими данными.** При будущем размещении обеспечить контроль доступа, резервное копирование и отдельные условия передачи внешним сервисам. ИИ-агроном отправляет контекст выбранного поля в DeepSeek.

## P1 — качество и устойчивость

3. **Частичная оценка рисков может восприниматься как полная.** Если из 4 факторов оценён только температурный и он низкий, прежний общий статус `low` сопровождался успокаивающим текстом. В этом PR добавлены `coverage_complete` и предупреждение о числе неизвестных факторов, при сохранении совместимого уровня карты.
4. **Весь обзор зависит от ответа OpenWeather по каждому полю.** `/api/dashboard` использует `asyncio.gather` без изоляции ошибки отдельного поля. При одном сбое API всего один ответ может сорвать загрузку остальных. Нужен режим partial results с чёткими метками свежести и отсутствия данных.
5. **Масштабирование.** Каталог хранится в JSON и защищён только локальным `threading.RLock`. Это не транзакционная БД и не гарантирует безопасные параллельные записи из нескольких процессов. Для сотен полей и многопользовательской работы нужен PostgreSQL с миграциями и индексами.
6. **Нет CI-проверки сборки в исходном main.** В этот PR добавлен workflow для pytest и `npm run build`. Реальные результаты увидим после запуска GitHub Actions.

## P2 — научная и продуктовая обоснованность

7. **Пороги погодных рисков — учебные.** Не проверены по культуре/фазе роста и не являются доказательством снижения потерь урожая. Для финала нужна тестовая выборка сценариев, протокол проверки и заключение агронома.
8. **Знания ИИ представлены локальными заметками.** Это ещё не полноценная база с версиями, первоисточниками и проверкой качества извлечения. Добавить ссылки на документы и строгую границу между данными и рекомендациями.
9. **Демонстрационные геометрии и прогнозы.** Необходимо явно маркировать их в UI, экспортируемых данных и видео, не смешивая с данными реальных хозяйств.
10. **История наблюдений без многопользовательских ролей и аудита изменений.** Для применения в хозяйстве нужна идентификация автора, контроль версий и журнал действий.

## Состав первого PR
