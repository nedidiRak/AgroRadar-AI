# AgroRisk Engine 4.0 — научный исследовательский слой (пилот)

Статус: **research preview**, не промышленный прогноз повреждения урожая. Основа — загруженные пользователем `AgroRadar_scientific_report.md`, `agrorisk_rules_research.json` и `AgroRadar_developer_spec.md` от 15.11.2026. Исследовательская база **реконструирована**, не является оригинальным полным набором из 152 записей.

## Реализовано

- Ровно **50 культур**, **85 записей**, **50 явных пропусков данных** — сохранены из переданного набора, с источниками и ограничениями, без «додумывания» критических температур.
- Поиск культуры и выбор стадии в форме поля. Старое поле `crop` и пользовательские текстовые описания сохраняются.
- Неоднозначные названия вроде «Пшеница» без выбора озимой/яровой формы не получают произвольный `crop_id`.
- Старый `risk_analysis` версии 3.0, четыре базовых фактора и окраска карты остаются нетронутыми.
- Новый `crop_risk_analysis` показывается отдельно для 24 часов и каждого из пяти прогнозных периодов.
- Поле **не становится зелёным** из-за отсутствия научного порога, стадии или требуемой температуры почвы.
- Пороговые эксперименты, физиологические диапазоны и коэффициенты Kc **не используются как аварийные пороги**.
- Поддерживаются только исследовательские подсказки по точкам прогноза воздуха и строго выбранной пользователем стадии (например, жара на цветении пшеницы). **Все** такие подсказки максимум жёлтые: `candidate`, никогда `high`.
- Ссылки на научные источники видны из интерфейса.
- Для автономной Windows-сборки JSON включён в PyInstaller как файл пакета.

## API

`GET /api/crops?query=&group=` — каталог; `GET /api/crops/{crop_id}/phenology` — исследовательские названия стадий (BBCH пока `null`).

`GET /api/risk-rules?crop_id=&stage=&factor=`, `GET /api/risk-rules/{rule_id}`, `GET /api/risk-rules/version` — данные и ссылки на источники.

`POST /api/risks/evaluate` — только явно помеченный `scenario`/`demo` с тестовыми точками, не изменяет поля и реальные оповещения.

`GET /api/fields/{id}/risks` и `GET /api/dashboard` дополнены ключом `crop_risk_analysis`. Старые ключи не удалены.

## Границы достоверности

Исследование содержит **ноль** правил, официально одобренных агрономом для практического применения. «Нет превышения предварительного ориентира» не приравнивается к «урожай в безопасности».

Важны отличия температуры воздуха на 2 м от почвы, узла кущения, корзинки подсолнечника и температурной экспозиции. Точки OpenWeather каждые 3 часа не равны непрерывным измерениям. Значения `temperature_c` / `minimum_temperature_c` не являются гарантированным фактическим экстремумом на поле.

Фазы, выбранные вручную, не подтверждают фактический BBCH; в этом этапе нет автоматического определения фенологии, полной модели водного баланса или истории `RiskEvent` в БД. Следующий шаг: экспертная проверка и версия одобренных правил, историческое тестирование на данных Центрального Черноземья и затем аккуратная интеграция в SQLite.

## Проверка

```shell
cd backend
python -m pytest -q tests/test_crop_risk_research.py tests/test_risk_engine_v3.py tests/test_five_day_forecast.py
cd ../frontend
npm ci
npm run build
```

Демонстрационный сценарий: два поля с одинаковым прогнозом +34 °C; первое — пшеница, стадия «Цветение», выдаёт жёлтый научный ориентир; второе — соя, стадия «Цветение», требует 14-дневной экспозиции и честно показывает «недостаточно данных». Это **иллюстративная проверка логики**, а не подтверждение реального риска урожая.
